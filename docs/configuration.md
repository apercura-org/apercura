# Configuration

Every setting is an environment variable, read from a single `.env` file at
the repository root (the web app, the import and the migrations share it) or
from the host's environment. The web app validates its variables at start-up
with the schema in `apps/web/src/env.ts`; `SKIP_ENV_VALIDATION=1` skips that
check (CI lint jobs, Docker image builds).

`bun run keys:generate` prints fresh values for every secret below that is
marked _generate_.

## Scheduled jobs (`bun run jobs:tick`)

One entry point for the host's scheduler (every 5 minutes is a good default), from the same
image as the app. It reads the web app's variables (`DATABASE_URL`, `DATABASE_URL_JOBS`,
`ENCRYPTION_*`, `BLIND_INDEX_KEY`, `SMTP_URL`, `MAIL_FROM`, `APP_URL`, the retention periods) and
chains:

- `expire`, `reminders` (the day before, from 09:00 in the site's time zone), `outbox` (emails);
- `closures`: practices closed with their owner's account (their upcoming appointments were
  cancelled and the patients emailed at once) lose their booking data, data keys and
  organization once those emails are out, or 24 hours after the closure at the latest;
- `next-free`: the next free slot of result cards and practitioner pages (when
  `REVALIDATE_SECRET` is set, it asks the app, `APP_URL/api/revalidate`, to refresh the cached
  pages whose next free time changed);
- `purge`: patient data at the end of its retention, unverified bookings after 24 hours;
- `claim-documents`: claim documents 30 days after their decision, and the photo and documents of
  a removed practitioner (`directory.storage_deletions`) (needs the S3 variables);
- `requests`: error reports and removal requests at the end of their retention after closure,
  "I am this practitioner" contact requests `CONTACT_REQUEST_RETENTION_MONTHS` after their last
  change;
- `page-views`: daily view counters older than `PAGE_VIEW_RETENTION_MONTHS`;
- `admin-alerts`: the administrators' batched alert of new claims and contact requests (one
  email per queue and `ADMIN_ALERT_INTERVAL_MINUTES` at most, to `ADMIN_NOTIFY_EMAIL`);
- `audit-log`: rows of both access logs older than `AUDIT_LOG_RETENTION_MONTHS`, over
  `DATABASE_URL_JOBS` (see above).

Each sub-job holds a Postgres advisory lock, so overlapping runs are harmless;
`bun run jobs:tick outbox` (or any name above) runs one of them. It refuses to run when the
overlap constraint is missing, and in production with an `SMTP_URL` that breaks the TLS rules.

### Cache warm-up (`bun run jobs:tick warm`)

Not part of the default tick: scheduled on its own line (`docker/crontab`,
`clevercloud/cron.json`), it requests the next slice of the site's sitemap URLs from the app so
they are rendered and cached before visitors and crawlers ask
([public-site.md](./public-site.md#cache-warm-up)). `jobs:tick warm --restart` starts the walk
over. It reads `APP_URL` (sent as the `Host`), `INTERNAL_APP_URL` (where the requests go; default
`APP_URL`) and:

| Variable                 | Default | Role                                                                                              |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------------- |
| `WARM_CACHE`             | `true`  | `false` (or `0`) turns the warm-up off: each run logs `{"skipped":"disabled"}`.                   |
| `WARM_CACHE_CONCURRENCY` | `4`     | Requests at a time (1 to 16).                                                                     |
| `WARM_CACHE_MAX_URLS`    | `5000`  | URLs per run, at most.                                                                            |
| `WARM_CACHE_MAX_SECONDS` | `240`   | Seconds per run, at most (keep it under the five minutes between two runs).                       |
| `WARM_CACHE_MAX_P95_MS`  | `3000`  | The run stops when the p95 latency of its last 100 requests exceeds this (the app is struggling). |

A run also stops when `/api/health` fails or takes over 2 seconds (checked before it starts and
every 15 seconds), on a 429 or 503 answer, and when errors pass a tenth of its requests. A
malformed value stops the job with an error naming the variable.

## Platform administrators

Administrators review claims (`/pro/admin/revendications`), error reports and
removal requests (`/pro/admin/signalements`). There is no sign-up for them:
an existing account with a second factor is promoted in the database, e.g.
`UPDATE directory."user" SET is_platform_admin = true WHERE email = '…';`.
The flag is read on every request; administrators never reach patient data,
and every document or message they decrypt is written to
`directory.platform_audit_events`.

| Variable                     | Role                                                                                                                        |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `VERIFY_IMAGE`               | PostGIS image `scripts/verify-backup.sh` restores into (default `postgis/postgis:17-3.7`).                                  |
| `VERIFY_PLATFORM`            | Platform of that image (default `linux/amd64`, the only one PostGIS publishes).                                             |
| `VERIFY_MIN_PRACTITIONERS`   | Fewest practitioners a restored dump must hold (default 1; 0 for a dump taken before the first import).                     |
| `VERIFY_EXPECTED_MIGRATIONS` | Migrations the restored dump must record (default: those of the checkout).                                                  |
| `PRODUCTION_URL`             | Repository **variable** (not a secret) read by `.github/workflows/uptime.yml`; the scheduled check skips while it is unset. |
| `UPTIME_PRACTITIONER_PATH`   | Repository variable: the practitioner page the uptime check fetches (default: the first page of the practitioner sitemap).  |
